# «Повод» — архитектурная спецификация MVP

**Дата:** 2026-10-08
**Версия:** 0.1
**Статус:** черновик для ревью владельцем проекта
**Тип решения:** один клуб, модульный монолит, без мультиарендности

## 1. Назначение документа

Документ фиксирует архитектуру первой версии Telegram-продукта клуба «Повод»:

- продажа билетов на мероприятия;
- управление мероприятиями и вместимостью;
- CRM клиентской базы;
- электронные билеты и контроль входа;
- массовые Telegram-рассылки;
- базовая аналитика источников, продаж и посещаемости.

Это проектное решение, а не план отдельных коммитов. До начала реализации документ должен быть просмотрен владельцем проекта. После утверждения на его основе будет создан детальный implementation plan.

## 2. Контекст и цели

«Повод» — один управляемый продукт для одного клуба. В первом релизе не требуется поддержка нескольких независимых организаций, но модель мероприятий должна позволять добавлять новые направления без переписывания ядра.

Главная цель MVP — дать клиенту короткий и надёжный путь:

```text
/start → афиша → мероприятие → количество билетов → временная бронь
       → оплата через Т‑Банк → подтверждение → QR-билет → проход
```

Организатор должен иметь возможность без изменения исходного кода создавать мероприятия, принимать оплату, видеть покупателей и посещения, проверять билеты и отправлять разрешённые рассылки.

## 3. Границы MVP

### Входит в MVP

1. Telegram-бот для клиентов на `aiogram 3`.
2. Регистрация пользователя и создание карточки CRM.
3. История согласий на обработку данных и рекламные рассылки.
4. Направления мероприятий как настраиваемые записи в базе.
5. Афиша и карточка мероприятия.
6. Типы билетов и ограничение вместимости.
7. Временная бронь мест.
8. Интернет-эквайринг Т‑Банка через API.
9. Идемпотентная обработка статусов платежа и возвратов.
10. Выдача электронных билетов с QR-токенами.
11. Проверка и одноразовое погашение билета.
12. Веб-админка в браузере.
13. Роли владельца, администратора и сотрудника на входе.
14. CRM: заказы, расходы, интересы, посещения и источники.
15. Рассылки по базе пользователей с действующим рекламным согласием.
16. Базовая атрибуция переходов и воронки.
17. Логи, аудит критических действий, резервное копирование и восстановление.
18. Unit-, интеграционные и сценарные тесты критической логики.

### Не входит в первый релиз

- мультиарендность и самостоятельная регистрация других клубов;
- нативные мобильные приложения;
- сложная реферальная программа;
- промокоды и динамическое ценообразование;
- абонементы и членство;
- сложные автоворонки;
- расширенная BI-аналитика;
- отдельные микросервисы;
- кастомные бизнес-процессы для каждого направления.

Эти функции не должны блокировать запуск базовой продажи билетов и CRM. При этом границы модулей должны позволить добавить их позднее.

## 4. Архитектурное решение

### Выбранный вариант

Используется модульный монолит:

- один репозиторий;
- один основной Python-код;
- общая PostgreSQL-база;
- отдельный процесс фоновых задач;
- FastAPI как API, webhook-слой и веб-админка;
- Telegram-бот как отдельный runtime-процесс, использующий общие сервисы;
- платёжный провайдер изолирован адаптером.

Модули разделяются по ответственности и не обращаются напрямую к таблицам друг друга в обход репозиториев и сервисов.

### Почему не микросервисы

Платежи, бронь мест, заказы и билеты требуют согласованных транзакций. На старте общая база и модульные границы дают меньше операционной сложности и ниже риск рассинхронизации. Разделение процессов допускается только там, где оно полезно уже в MVP: bot, API и worker могут запускаться отдельно, оставаясь частью одного приложения.

### Технологический стек

- Python 3.12+;
- `aiogram 3`;
- `FastAPI` и `Uvicorn`;
- `SQLAlchemy 2` в асинхронном режиме;
- PostgreSQL;
- Alembic;
- `Pydantic Settings` для конфигурации;
- `httpx` для внешних API;
- Redis и Python-совместимый worker для отложенных задач и очереди рассылок;
- Jinja2/HTMX или эквивалентный лёгкий web UI внутри FastAPI для первой админки;
- Docker Compose для локальной разработки и первого развёртывания;
- pytest, pytest-asyncio и интеграционные тесты с изолированной БД.

Конкретные версии библиотек фиксируются в `pyproject.toml` после проверки совместимости. Внешние зависимости не должны получать секреты из исходного кода.

## 5. Компоненты и границы

### `bot`

Отвечает за Telegram update handlers, клавиатуры, пользовательские сценарии и отображение ошибок. Бизнес-правила покупки, оплаты и выдачи билетов не должны находиться в обработчиках Telegram.

### `api`

Отвечает за:

- HTTP API для админки;
- webhook Telegram в production;
- webhook Т‑Банка;
- health/readiness endpoints;
- сериализацию входных и выходных данных;
- аутентификацию и авторизацию административных запросов.

### `admin`

Отвечает за web-интерфейс владельца, администратора и сотрудника на входе. UI использует API и сервисный слой, а не меняет модели напрямую.

### `services`

Основные сервисы:

- `users` — пользователи и профиль Telegram;
- `consents` — согласия, версии текстов, отзыв и удаление данных;
- `directions` — направления и интересы;
- `events` — мероприятия, статусы, вместимость и публикация;
- `orders` — заказ и его state machine;
- `reservations` — временная бронь и освобождение мест;
- `payments` — общий контракт платежей и обработка статусов;
- `tickets` — выдача, QR-токены и погашение;
- `campaigns` — рассылки, сегменты и результаты доставки;
- `analytics` — атрибуция и агрегаты;
- `audit` — критические действия сотрудников.

### `repositories`

Изолируют SQL-запросы, транзакции и блокировки строк. Сервисный слой определяет правила, repository-слой выполняет операции с базой.

### `workers`

Выполняет отложенные операции:

- освобождение истёкших броней;
- отправку рассылок с ограничением скорости;
- напоминания;
- генерацию тяжёлых экспортов;
- периодические проверки и технические задачи.

Повторный запуск задачи не должен создавать дубликат платежа, билета, рассылки или уведомления.

## 6. Направления мероприятий

Направление — это данные, а не enum в коде.

Минимальные свойства направления:

- `id`;
- уникальный `slug`;
- отображаемое название;
- описание;
- обложка или цвет оформления, если понадобится UI;
- порядок отображения;
- признак активности;
- дата создания и изменения.

На старте можно завести направления «Кино», «Книги» и «Мастер-классы». Новое направление добавляется через админку и не требует выпуска новой версии приложения.

В MVP все направления используют общий сценарий покупки. Особые сценарии — бесплатная регистрация, абонементы, депозит, повторяющиеся занятия — добавляются как отдельные типы бизнес-процесса только после появления реального требования.

## 7. Модель данных

Основные сущности:

1. `users` — Telegram-пользователь, профиль, даты регистрации и последней активности.
2. `consents` — неизменяемая история согласий, отзывов, версии текста, способа и времени получения.
3. `directions` — справочник направлений.
4. `user_interests` — связь пользователя с направлениями и источник изменения.
5. `events` — мероприятие, направление, описание, дата, часовой пояс, адрес, карта, статус и вместимость.
6. `ticket_types` — название, цена, лимит, активность и связь с мероприятием.
7. `reservations` — временная бронь, срок действия и состав зарезервированных билетов.
8. `orders` — заказ, пользователь, мероприятие, сумма, валюта, состояние и сроки.
9. `order_items` — количество и цена каждого типа билета на момент покупки.
10. `payments` — провайдер, внешний идентификатор, внутренний заказ, сумма, статус, timestamps и сведения о возврате.
11. `payment_events` — входящие события провайдера с deduplication key и исходным безопасным payload.
12. `tickets` — билет, заказ, мероприятие, тип, непредсказуемый токен и состояние.
13. `checkins` — факт входа, время, сотрудник и устройство/источник проверки.
14. `campaigns` — рассылка, сегмент, сообщение, состояние и расписание.
15. `campaign_deliveries` — состояние доставки конкретному пользователю, ошибки и переходы.
16. `attribution` — первоначальный и последний известный источник, `start`-параметры и связанные события воронки.
17. `admin_users` и `admin_roles` — административные аккаунты и права.
18. `admin_audit_logs` — критические действия, субъект, объект, время и результат.

### Ключевые ограничения

- Telegram ID уникален.
- `slug` направления уникален.
- Нельзя опубликовать мероприятие без даты, цены/типа билета, часового пояса и вместимости.
- Сумма заказа рассчитывается на сервере по зафиксированной цене `order_items`.
- Количество проданных и зарезервированных мест не может превышать вместимость.
- Внешний идентификатор платежа уникален в рамках провайдера.
- Один входящий платёжный event не применяется повторно.
- QR-токен хранится в безопасном виде и не является последовательным ID.
- Билет в состоянии `checked_in` нельзя погасить повторно.
- Рассылка не отправляется пользователю без действующего согласия на рекламу.
- Удаление или обезличивание пользователя не должно разрушать финансовый аудит, если запись требуется хранить по закону; связи должны быть спроектированы отдельно.

## 8. Состояния бизнес-объектов

### Мероприятие

`draft` → `published` → `sold_out` / `completed`; из `published` также допускается `cancelled`.

Переходы проверяются сервисом мероприятий, а не UI.

### Бронь

`active` → `converted` при успешной оплате; `active` → `expired` по сроку; `active` → `released` при отмене или явном освобождении.

Истёкшая бронь должна освобождать места как worker-задачей, так и ленивой проверкой при новой покупке.

### Заказ

`pending_payment` → `paid`; `pending_payment` → `payment_failed`; `pending_payment` → `expired`; `paid` → `refund_requested` → `refunded`.

Дополнительно фиксируются `cancelled` и техническое состояние `reconciliation_required`, если состояние провайдера не удалось однозначно сопоставить.

### Платёж

Хранится внутреннее состояние и исходный статус Т‑Банка. Переходы должны быть идемпотентными и монотонными, кроме явно разрешённых операций возврата/отмены.

### Билет

`issued` → `checked_in`; `issued` → `voided` при возврате или аннулировании.

`checked_in` не возвращается в действующее состояние без отдельной административной процедуры.

## 9. Платёжная интеграция с Т‑Банком

Используется API Интернет-эквайринга Т‑Банка, подключённый к кабинету Т‑Бизнеса. Нельзя смешивать его с API исходящих банковских платежей или с общим API выставления счетов.

Официальные сценарии и текущие контракты необходимо сверять при реализации по документации Т‑Банка:

- [Проведение платежей](https://developer.tbank.ru/ecosystembundle/scenarios/payments);
- [Статус платежа](https://developer.tbank.ru/docs/intro/webhooks/payment-status);
- [Добавление webhook](https://developer.tbank.ru/docs/api/add-webhook).

### Базовый поток

1. Клиент выбирает мероприятие и количество билетов.
2. Сервис бронирования в транзакции резервирует места.
3. Сервис заказов создаёт заказ со статусом `pending_payment`.
4. Сервер создаёт платёж в Т‑Банке.
5. Система сохраняет внешний идентификатор и `PaymentURL`.
6. Бот отправляет клиенту кнопку перехода на платёжную форму.
7. Клиент оплачивает на стороне Т‑Банка.
8. Система принимает и проверяет webhook статуса.
9. Только подтверждённый статус переводит заказ в `paid`.
10. После подтверждения создаются билеты и отправляются клиенту.
11. При ошибке или истечении оплаты бронь освобождается.

Редирект клиента, текст кнопки или факт возврата из платёжной формы не считаются подтверждением оплаты. Источником истины является проверенный ответ API/webhook Т‑Банка.

### Надёжность платежей

- Внутренний `order_id` не равен внешнему ID без явного маппинга.
- Запрос создания платежа и ответ провайдера журналируются без секретов и платёжных реквизитов.
- Повторное событие для одного платежа не создаёт второй заказ или второй комплект билетов.
- Неизвестный статус не переводит заказ в `paid`; он попадает в очередь сверки.
- Подтверждение, пришедшее после истечения брони, обрабатывается отдельным правилом: система не продаёт сверх вместимости, а заказ переводится на ручную сверку/возврат в зависимости от фактического статуса и политики клуба.
- Возврат меняет состояние платежа и билетов в одной согласованной бизнес-операции; повторный запрос возврата безопасен.
- Чеки и фискализация включаются в интеграцию, если это требуется условиями подключения и законодательством.
- Webhook endpoint работает по HTTPS и использует предусмотренный Т‑Банком механизм аутентификации. Секрет webhook хранится в окружении.

## 10. Бронирование и защита от перепродажи

Покупка последних мест должна быть атомарной.

Рекомендуемый MVP-механизм:

1. Открыть транзакцию.
2. Заблокировать строку мероприятия или другой единый счётчик мест через `SELECT ... FOR UPDATE`.
3. Освободить истёкшие брони для этого мероприятия.
4. Посчитать проданные и активные зарезервированные места.
5. Проверить остаток.
6. Создать заказ и бронь с единым сроком истечения.
7. Зафиксировать транзакцию.
8. Создать платёж после успешной фиксации брони.

Если платёж не был создан, бронь должна быть освобождена. Если внешний API временно недоступен, заказ не должен считаться оплаченным.

## 11. Telegram-сценарии

### Клиент

- `/start` с сохранением первого `start`-параметра;
- приветствие и согласия;
- афиша по направлениям и датам;
- карточка мероприятия;
- выбор типа и количества билетов;
- подтверждение заказа;
- переход к оплате;
- результат оплаты;
- «Мои билеты»;
- QR-код и детали мероприятия;
- настройки уведомлений;
- отписка от рекламы;
- поддержка.

Навигация строится на inline-кнопках. Все ключевые сценарии имеют возврат в главное меню и восстанавливаются после перезапуска за счёт состояния в базе, а не только памяти процесса.

### Администратор

Веб-админка должна позволять:

- управлять направлениями;
- создавать, публиковать, редактировать и отменять мероприятия;
- управлять типами билетов и вместимостью;
- видеть заказы, платежи и возвраты;
- просматривать список гостей;
- проверять и аннулировать билеты;
- управлять пользователями и сегментами;
- создавать, тестировать, планировать и отменять рассылки;
- смотреть базовые отчёты;
- видеть аудит критических действий.

## 12. CRM, согласия и персональные данные

При первом `/start` создаётся или обновляется пользователь. Обновление имени и username не должно создавать новую карточку.

Отдельно фиксируются:

- согласие на обработку персональных данных;
- согласие на рекламные рассылки;
- версия текста согласия;
- дата и способ получения;
- отзыв согласия;
- запрос на удаление/обезличивание;
- основание для хранения финансовой и аудиторской информации.

Проверка рекламного согласия выполняется непосредственно перед каждой отправкой, а не только при формировании сегмента. Блокировка бота, ошибка отправки и отказ пользователя сохраняются в истории доставки.

Юридические тексты и основания обработки должны быть утверждены владельцем бизнеса и профильным специалистом до коммерческого запуска. Архитектура не заменяет юридическую проверку.

## 13. Права доступа и аудит

### Владелец

Полный доступ к настройкам, мероприятиям, платежам, CRM, рассылкам, ролям и аудиту.

### Администратор

Управление мероприятиями, заказами, CRM и рассылками в пределах предоставленных прав. Доступ к секретам и системным настройкам исключается.

### Сотрудник на входе

Только поиск и проверка билета, просмотр минимально необходимых данных гостя и фиксация входа.

Критические действия аудируются:

- изменение мероприятия и цены;
- ручное изменение заказа;
- возврат или аннулирование билета;
- изменение согласия или доступа сотрудника;
- запуск, отмена и изменение рассылки;
- экспорт персональных данных.

## 14. API и внешние интерфейсы

Внутренние контракты проектируются вокруг бизнес-операций, а не вокруг таблиц.

Основные группы endpoint:

- `/api/admin/directions`;
- `/api/admin/events`;

## 15. Фоновые задачи и согласованность

Для задач, которые нельзя надёжно выполнять внутри Telegram update или HTTP-запроса, используется worker:

- истечение броней;
- повторная доставка сообщений с контролируемой политикой;
- рассылки с rate limit;
- напоминания;
- сверка платежей;
- экспорт CRM;
- агрегирование аналитики.

Для важных событий применяется transactional outbox или эквивалентный механизм: бизнес-изменение и постановка события на обработку фиксируются согласованно. Обработчик обязан быть повторяемым.

## 16. Безопасность

- Секреты Telegram, Т‑Банка, PostgreSQL и Redis находятся только в environment/secret storage.
- В Git хранится только `.env.example` без рабочих значений.
- Админка защищается HTTPS, сессионной авторизацией и RBAC.
- Webhook-и имеют отдельные маршруты и проверку аутентификации.
- В логах запрещаются токены, секреты, полные персональные данные и платёжные реквизиты.
- Входные данные валидируются на границе API и бота.
- Для запросов к БД используется параметризация ORM/драйвера.
- Экспорт CRM доступен только соответствующим ролям и аудируется.
- Резервные копии шифруются и регулярно проверяется восстановление.
- Перед коммерческим запуском выполняется проверка утечек секретов и персональных данных.

## 17. Наблюдаемость и эксплуатация

Минимально нужны:

- структурированные логи с correlation ID;
- отдельные события для заказа, платежа, брони, билета и webhook;
- health/readiness проверки;
- алерты по ошибкам платежей, росту неразобранных webhook, переполнению очереди и недоступности БД;
- метрики успешных/неуспешных платежей, конверсии и доставки рассылок;
- процедура ручной сверки неясных платежей;
- документированное восстановление из резервной копии.

## 19. Последовательность реализации

После утверждения спецификации реализация выполняется отдельными небольшими задачами:

1. Репозиторий, `AGENTS.md`, документация, конфигурация и CI.
2. Скелет приложения, health checks, PostgreSQL, Alembic и логирование.
3. Пользователи, `/start`, профиль, согласия и направления.
4. Мероприятия, типы билетов и админские роли.
5. Бронь, заказы и защита от перепродажи.
6. Адаптер Т‑Банка, sandbox-платежи и webhook-обработка.
7. Билеты, QR-коды и check-in.
8. CRM, сегменты и базовая атрибуция.
9. Админка для управления мероприятиями, заказами и билетами.
10. Рассылки, очередь, отписка и отчёты доставки.
11. Интеграционные сценарии, безопасность, резервные копии и восстановление.
12. Приёмочное тестирование MVP.

Каждая задача получает критерии готовности, тесты и отчёт. Новый этап не считается завершённым только по факту написания кода.

## 20. Критерии готовности MVP

MVP считается готовым, когда в тестовой и затем рабочей среде подтверждены следующие сценарии:

- новый пользователь создаётся в CRM без дубля при повторном `/start`;
- пользователь видит направления и афишу;
- администратор создаёт мероприятие и лимит мест;
- пользователь создаёт заказ и получает временную бронь;
- платёж проходит через API Т‑Банка;
- повторный webhook не создаёт повторную оплату или билет;
- при успешном платеже выдаётся действующий QR-билет;
- организатор проверяет билет и повторный вход блокируется;
- последние места нельзя продать дважды при конкурентной покупке;
- возврат меняет состояние платежа и билета;
- рассылка уходит только пользователям с действующим согласием;
- отписка реально исключает пользователя из следующих рекламных отправок;
- административные права соблюдаются и критические действия аудируются;
- сервис восстанавливается после перезапуска;
- резервная копия восстанавливается на проверочном окружении;
- обязательные тесты и проверки безопасности проходят.

## 21. Решения, которые остаются на следующем этапе

Эти вопросы не меняют выбранную архитектуру, но должны быть зафиксированы до реализации соответствующего модуля:

- точный набор способов оплаты, включённых в кабинете Т‑Банка;
- окончательный дизайн и визуальная стилистика админки;
- способ административной авторизации: локальные аккаунты, T‑ID или другой согласованный механизм;
- конкретный worker-пакет поверх Redis;
- хостинг и стратегия размещения PostgreSQL;
- точные юридические тексты, правила хранения и порядок удаления данных;
- политика возвратов и поведение при подтверждении оплаты после истечения брони;
- часовой пояс клуба и правила перехода на летнее/зимнее время;
- состав первоначальных сегментов рассылки и событий атрибуции.

Эти решения нельзя скрывать внутри кода: каждое должно быть отражено в `docs/DECISIONS.md`.
