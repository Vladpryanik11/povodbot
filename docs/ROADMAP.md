# «Повод» — утверждённый roadmap MVP

Источник: разделы 19–20 утверждённой архитектурной спецификации
`superpowers/specs/2026-10-08-povod-mvp-design.md`.
Статус: основные срезы Tasks 1–9 реализованы в изолированной ветке и проходят
полные локальные проверки. Внешняя проверка T‑Bank sandbox, Telegram runtime и
изолированное восстановление backup требуют credentials и инфраструктуры
владельца до коммерческого запуска. Task 1 объединяет foundation из первых двух
этапов.

## Последовательность реализации

1. Репозиторий, `AGENTS.md`, документация, конфигурация и CI.
2. Скелет приложения, health checks, PostgreSQL, Alembic и логирование.
3. Пользователи, `/start`, профиль, согласия и направления.
4. Мероприятия, типы билетов и админские роли.
5. Бронь, заказы и защита от перепродажи.
6. Адаптер Т‑Банка, sandbox-платежи и webhook-обработка.
7. Билеты, QR-коды и check-in.
8. CRM, сегменты и базовая атрибуция.
9. Админка для управления мероприятиями, платежами и билетами.
10. Рассылки, consent-gate, attribution и базовые отчёты доставки.
11. Интеграционные сценарии, безопасность, резервные копии и восстановление.
12. Приёмочное тестирование MVP.

В текущей ветке собраны пункты 1–10 в коде и тестах; пункты внешней
эксплуатационной проверки остаются release-gates, а не считаются пройденными по
наличию исходников.

Каждая задача получает критерии готовности, тесты и отчёт. Новый этап не считается
завершённым только по факту написания кода. Alembic и модели — Task 2 плана.

## Критерии готовности MVP

- новый пользователь создаётся в CRM без дубля при повторном `/start`;
- пользователь видит направления и афишу;
- администратор создаёт мероприятие и лимит мест;
- пользователь создаёт заказ и получает временную бронь;
- платёж проходит через API Т‑Банка;
- повторный webhook не создаёт повторную оплату или билет;
- при успешном платеже выдаётся действующий QR-билет;
- организатор проверяет билет и повторный вход блокируется;
- последние места нельзя продать дважды при конкурентной покупке;
- возврат меняет состояние платежа и билета;
- рассылка уходит только пользователям с действующим согласием;
- отписка реально исключает пользователя из следующих рекламных отправок;
- административные права соблюдаются и критические действия аудируются;
- сервис восстанавливается после перезапуска;
- резервная копия восстанавливается на проверочном окружении;
- обязательные тесты и проверки безопасности проходят.

## Неизменяемые ограничения

Один клуб, без мультиарендности. Направления — записи таблицы, добавляемые без
релиза. Общий путь: мероприятие → билеты → бронь → Т-Банк → подтверждение → QR → вход.
TTL брони 600 секунд; освобождение worker и ленивой проверкой. Только проверенный
статус банка подтверждает оплату. Дубли и переставленные webhook не создают
повторных заказов, билетов или возвратов. Суммы вычисляет сервер по зафиксированной
цене order_items. Telegram ID, slug направления, внешний ID платежа/провайдер
и webhook deduplication key уникальны. Рекламное согласие проверяется перед самой
доставкой. QR непредсказуем, повторный вход запрещён. Нет секретов, персональных
данных и платёжных реквизитов в Git и обычных логах. Все времена timezone-aware;
системные timestamps UTC, timezone мероприятия явно сохранён. TDD и полный набор
проверок предшествуют завершению среза и отдельному коммиту в изолированном worktree.
