# Архитектурные решения

## ADR-001: Модульный монолит — принято

Один репозиторий и PostgreSQL, отдельные процессы API/bot/worker с общими
сервисами. Это сохраняет транзакционную согласованность брони, платежа и билета
при небольшой операционной сложности. Модули общаются через сервисы/репозитории.

## ADR-002: Интернет-эквайринг Т-Банка — принято

Платежи идут через API интернет-эквайринга, изолированный PaymentGateway.
Редирект не подтверждает оплату; проверенный статус провайдера — источник истины.
Контракты, аутентификация webhook, sandbox и возвраты проверяются в Task 5.
API исходящих банковских платежей не является выбранной интеграцией.

## ADR-003: Один клуб — принято

Мультиарендность и организации исключены из MVP. Направления хранятся как данные,
поэтому новые направления не требуют нового релиза или нового процесса покупки.

## ADR-004: Foundation fixtures — принято для Task 1

Приложение принимает только PostgreSQL async URL. CI использует disposable
PostgreSQL. Локальный fallback SQLite проверяет только readiness и базовые
транзакции; он не подтверждает PostgreSQL locks, migrations или concurrency.
Следующие задачи с моделями/блокировками должны проверяться на PostgreSQL.

## Открытые решения до соответствующего модуля

- Способы оплаты в кабинете Т-Банка, фискализация и sandbox-контракты.
- Дизайн админки и согласованный способ административной авторизации.
- Worker-пакет поверх Redis и хостинг PostgreSQL.
- Юридические тексты, сроки хранения, удаление/обезличивание и финансовый аудит.
- Политика возвратов и поздней оплаты после истечения брони.
- Часовой пояс клуба (не выводить автоматически из компьютера разработчика).
- Первоначальные сегменты рассылок и события атрибуции.

Решения не скрывать внутри кода; фиксировать до реализации соответствующего среза.
